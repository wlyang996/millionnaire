## 实施前代码证据（历史调研）

- `server/.../config/RentInflation.java`：默认前 10 轮租金不变，第 11～15 轮 120%，16～20 轮 140%，最多 300%；仅破产模式有效。原值可通过后台调整。

- `server/.../core/engine/EconomyModule.java`：现有租金先处理同组加成、再处理轮次倍率，每一步按当前规则向下取整到 10。不能改掉既有计算顺序。

## 一、全员轮次收入奖励

### 触发规则

- `rewardRound` 指已完成的整轮数。默认拟为 5：第 5 轮全部存活玩家行动完成后、下一轮开始前发放，不能第 5 个玩家回合就发。
- 一局只发一次。未达到该轮便结束的局不补发。正常结束与奖励同时到达时，结束优先。
- 为确保整轮公平：在当前玩家经济结算、移动、抽卡、小游戏、欠款、响应及已启动的交易/拍卖全部完成后才进入奖励；不能在正在筹集欠款时发奖励救活玩家。
- 只给发放时存活的玩家，含机器人、托管和掉线但未淘汰的玩家。已破产、认输者不领，观战者仅观看。
- 达到奖励轮次时，在安全点一次性冻结所有玩家的累计收入快照，再计算奖励并入账。不能逐个发放导致前一人的奖励进入后一人的统计。
- 收入来源配置采用固定白名单，不能由管理员输入任意账本 reason 字符串。

### 收入定义

默认计入：

- 实际收取的地产、车站租金，包括通过欠款筹资和破产清算实际收到的租金部分。
- 实际到账的经过起点奖励。
- 事件和起点抽卡中的现金奖励。
- 虎口拔牙小游戏现金奖励。
- 无主地拍卖发起人的实际佣金（收入来源可单独关闭）。

默认排除：

- 开局资金、冻结/解冻、抵押所得、资产清算卖出款、赎回资金变化。
- 交易、拍卖卖出款、被强制购房所得：均属于资产换现金。
- 尚未支付的应收租金、被免租金额、地产估值增长。
- 本次轮次奖励以及将来增加的系列赛奖励，避免奖励再生奖励。

统计正向到账额；后续买地、升级、缴租等支出不冲减累计收入。因此“当前现金 2000”和“累计玩法收入 8000”可以同时成立。

欠款支付必须根据 `DebtState.source.kind == RENT` 归类，并统计实际付给债权人的数额；不能将所有 `DEBT_PAYMENT` 和 `DEBT_SETTLEMENT` 都视为收租，也不能在 `RentCharged` 和支付事件上重复计数。

### 奖励计算

`原始奖励 = floor(累计玩法收入 × rewardPercent / 100)`

`奖励 = floor(min(原始奖励, perPlayerCap) / roundingUnit) × roundingUnit`

默认 5%，封顶 1000，拟定取整单位 10；累计收入为 0 或计算结果为 0 时显示 +0，不生成零额账本分录。封顶须是取整单位的整数倍，保证上限含义明确。计算使用精确整数和溢出检查，不使用浮点金额。

例：累计收入 8000 → +400；6000 → +300；25000 → 原始 1250、封顶后 +1000。奖励由系统账户转给玩家，账本仍保持守恒。

### 全局 UI 与同步

- 独立全屏奖励提醒，隐藏棋盘并阻断棋盘输入；背景沿用小镇风格。
- 同一份公开结果展示头像、昵称、累计收入、本次奖励；本人行突出，8 人列表可滚动。并非新建一个收入排行榜，示例奖牌不作为正式排名规则。
- 自己仍存活时显示“你的奖励 +N”；自己已淘汰或为观战者时显示“本轮奖励已发放”，不伪造本人领款。
- 底部“3 秒后继续”是剩余展示时间，不是点击领取。奖励自动到账；机器人、掉线无需点击，某一玩家关闭本地页面不会推进全局流程。
- 服务端下发 `noticeId / opensAt / endsAt / awards`；到同一 `endsAt` 自动继续。重连显示真实剩余时间，过期提醒不重播、不再发钱。
- 上方玩家资金正向飘字使用现有机制，展示结束时同步余额；底栏不恢复被用户删除的现金。
- 下一位投骰/监狱判定的 `opensAt` 必须晚于最后一段旧动画和全局提醒的 `endsAt`。快速模式缩放展示缓冲，继续沿用普通移动 550ms/格，不改人物速度和玩家操作时限。
- 限时模式全局局时继续走；提醒属于局内用时。如果提醒期间局时到达，已入账奖励保留，展示结束后进入结算，不再开投骰窗口。

### 后台配置

新增 `RoundRewardConfig` / `GameSettings.RoundRewardSetting`：

- enabled：开关；拟定新配置默认开启。
- timeLimitRewardRound、bankruptcyRewardRound：两种模式分别配置，拟定默认 5；范围 1～1000。
- rewardPercent：0～100，默认 5；0 表示金额为 0，但开关负责是否展示该玩法。
- perPlayerCap：0～1000000，默认 1000。
- roundingUnit：固定可选 1/10/50/100，拟定默认 10。
- incomeSources：默认以上五类；使用固定枚举白名单，允许管理员勾选。
- presentationMs：1000～10000，拟定默认 3000；实际按房间快速模式统一换算。

管理页提供计算预览（输入累计收入 → 奖励），并说明第 N 轮完成时触发、与现有租金上涨独立。

## 二、结算趣味称号

默认提出四种，属于展示荣誉，不产生额外奖励：

1. 收租王：全局实际收租金额最多。包括租金债务实际偿付，免租不计；最低有效金额可配置，拟定 1。
2. 地产大亨：本局同时持有房产数量的峰值最高，普通地产与车站分别列出；最低有效数量拟定 1。必须记录峰值，不能在结算时只看已被清算的资产。
3. 幸运之星：现金事件与小游戏实际奖励合计最多，排除起点固定奖励、租金、轮次奖励；最低有效金额拟定 1。
4. 逆风翻盘：在奖励轮次边界、奖励入账之前记录净资产名次，结束时名次上升最多且仍存活；拟定至少上升 2 名。游戏未达到观察轮次、只有 1 人、或无人满足条件则不展示。

观察净资产名次的时机独立于轮次奖励开关：关奖励不能破坏逆风翻盘。参照同模式的配置轮次建立观察快照；淘汰者不能作为最后获奖者。并列按现有净资产/现金排名语义算名次，不能人为拆开并列。

同一称号同指标并列则共同获得，不用随机挑选；同一玩家可以获得多个称号。无有效数据就隐藏该称号，不编造胜者。

`FunTitleConfig` / `GameSettings.FunTitleSetting` 包含总开关、各称号开关、中文名称、统计阈值、逆风最低名次提升。名称限 2～12 字，固定指标类型不可任意替换。结算页在现有净资产排名下显示称号区，支持滚动，并给每项展示“为什么获奖”的真实指标。战绩详情只补获奖信息，不恢复用户删除的下方对局记录。

新增 `GameResult` 的公开指标与称号结果；客户端绑定服务端结果，不能自己决定获奖者。结算存储也要保存获奖快照，避免离开房间、重连或升级后丢失。

## 三、城市全局事件

这是房间共享事件，与个人事件格抽卡、幸运/不幸卡分别处理。

### 首版事件池

拟定默认均等权重，逐项可关闭、改名称、改倍率、改持续轮数：

- 建设节：普通地产付费升级费 ×80%，持续 2 整轮。
- 旅游旺季：车站租金 ×150%，持续 2 整轮。
- 安居日：普通地产租金 ×80%，持续 2 整轮。

首版不增加每轮发现金、无故扣钱或改变骰子点数，便于与现有经济流程组合验证。未来新效果必须新增固定引擎枚举，不在后台执行任意脚本。

建设节只折扣实际升级支付价格；买价、标准价值、抵押/赎回本金、强制购房报价与拍卖基数仍沿用现有规则，不降低资产账面价值。免费建造卡仍为免费，不另送折扣现金。升级价向下取整到整数，最低为 1。

租金事件计算顺序：原租金 → 既有同组加成 → 既有轮次上涨（保留原有每步取整）→ 城市倍率（向下取整到 10）。抵押不收租、免租、车站未抵押数量等规则不变。服务端下发基础价格、实际支付价、适用倍率，客户端购买/升级/详情页显示同一份报价；零租金不创建零额付款事件。

### 触发与轮次

- 拟定默认每完成 5 整轮进行一次触发检查，触发概率 30%；未触发就是正常继续，不显示空公告。
- 成功后按启用事件权重选择一项：完成第 5 轮时预告，默认提前 1 轮，第 6～7 轮生效，第 8 轮开始前结束。
- 只在整轮交界检查，不在每个玩家回合独立抽取。破产后存活人数变化仍按已有 `round` 语义判断，不改变行动顺序。
- 至多一个待生效/生效事件，不叠加。存在事件时跳过新的触发检查，不累计补抽；到期边界先结束旧事件，再判断是否处于本次检查周期。
- 开局不立即触发；首次检查轮次可独立配置。所有随机走引擎确定性 RNG，添加专用 DrawPoint，服务端记录选择结果；客户端不得抽选。
- 时间限制到达、全员托管结束、最后玩家结束等情况优先终止；不在 DRAINING 新建城市事件，也不为事件强行延长局时。

### 公告与常驻提示

- 全局预告是单独提醒页，隐藏棋盘；显示事件插画、名称、生效起止轮次、影响范围和倍率。自动同步结束，首次不要求逐人确认。
- 生效与结束以短非阻断横幅提示，并有明确的只读详情入口。常驻胶囊位于玩家区下、棋盘上，显示“建设节 · 升级费 ×80% · 剩余2轮”。事件牌的提示图仅定义胶囊新增区域，不重新定义棋盘格数、土地尺寸与人物动效。
- “剩余轮数”含当前轮：第 6 轮显示 2，第 7 轮显示 1，第 8 轮删除。预告期间显示“下轮生效”；后台提前轮数更大时显示对应轮次。
- 城市事件详情统一复用已确认的预告版式，以服务端真实状态呈现“待生效 / 生效中 / 已结束”，增加返回控件；具体详情/结束态补稿要在接入前完成并审阅。
- 与轮次奖励同边界发生时串行：结束旧城市事件 → 轮次奖励全屏 → 新事件预告全屏 → 开始下一轮 → 生效提示。动画、提示结束时再开放玩家操作窗口；不能同时叠两个弹层。
- 接入既有显示队列；`noticeId` 去重，活动状态与最近公告写入快照，重连和观战都能正确恢复。客户端清理队列后立刻同步所有玩家金钱。

### 后台配置

新增 `CityEventConfig` / `GameSettings.CityEventSetting`：

- enabled、allowedModes：总开关与生效模式，拟定限时/破产都可用。
- firstCheckRound、checkEveryRounds：拟定 5 / 5，范围 1～1000 / 1～100。
- triggerPercent：0～100，拟定 30。
- advanceRounds：提前轮数 1～10，拟定 1。
- announcementMs：1000～10000，拟定 3000；生效/结束提示时长分别可配置（拟定 1500ms）。
- pool：固定效果类型、启用、中文名称、权重 0～1000、multiplierPercent 1～300、durationRounds 1～20、现有/经确认的 artworkKey。
- 全部关闭或权重和为 0 时按无事件处理；拒绝重复效果类型与未知素材 key，未授权素材不自动生成。

后台提供事件概率/起止轮次预览、与租金上涨及同组加成组合的计算示例。管理员发布只影响下一批新房间的配置快照，在途对局不动态换规则。

## 四、实现分层与兼容

### 引擎（Java 21）

- `RuleConfig` 加三个类型化配置并在 `RuleConfigs.defaultV1()` 填默认，`ConfigValidator` 校验数值、枚举、交叉约束。
- `GameState` 加 `GameProgressState`，持有每人指标、观察轮次排名、奖励已发标记、城市事件与公告状态；默认空值兼容旧构造。
- 新增 `GameProgressModule`：由真实付款/产权事件演化指标；实际支付只计一次，同一事实不能同时从账本和事件两边累加。
- 新增公开事件：`RoundRewardGranted`（一批获奖快照与唯一编号）、`CityEventAnnounced/Activated/Ended`、`GlobalNoticeOpened/Closed`；账本分别产生 `ROUND_REWARD` 分录，统计排除该 reason。
- 与当前 reducer 一样对派生金额、轮次、中奖 RNG 和接续条件进行校验，不能相信客户端提交的奖励额或倍率。
- `GameView` 仅下发公开统计、公告、活动事件，手牌与 RNG 仍私有；`GameResult` 保留结算指标/获奖快照。
- `TurnModule.nextTurn` / 安全点接续需要保存 BeginTurn 等正确恢复位置。全局公告计时由服务端任务驱动，并计入新窗口 earliest-open，不用客户端延迟假装暂停。
- 关卡派生报价在 `EconomyModule` 统一入口应用事件倍率，欠款创建之后其应付额保持锁定，不能随事件结束变化。

### 网关与管理（现有 Spring 网关 + Vue 管理页）

- `GameSettings` 加配置项，`SettingsMapper` 默认补齐、中文范围提示、百分比/轮次换算、稳定排序。
- 旧管理快照缺新字段时补齐为“关闭”，不让历史版本因升级突然加入新规则；新默认配置开启需通过新发布版本。规则内容哈希不复用，旧对局使用原配置，具体旧规范序列化哈希兼容需测试，不以 record 默认值代替迁移策略。
- `/api/configs/{id}/client` 下发展示需要的规则；房间可见规则摘要说明奖励轮次、比例上限和城市事件是否开启。
- `RoomService` / WS 投影支持公告与称号数据，服务端时钟传真实起止；完整状态同步时不遗漏机器人指标。
- `web-manage/src/App.vue` 增加“轮次奖励”“城市事件”“结算称号”编辑区域、示例预览和说明；发布后构建到 `gateway/src/main/resources/static/admin`。
- 战绩需要保存称号/指标快照：优先增加 JSON 结果列并由 `GameRecords` 读取，确需表结构时新建下一个 Flyway 版本。当前目录最新为 V2，应重新确认后再新增 V3；禁止修改 V1/V2，兼容 MySQL 5.7 与 H2。

### 客户端（保持 Cocos Creator，不迁移 Vue）

- 管理后台继续 Vue，游戏继续 Cocos；没有引入第二套游戏前端的需求。
- `Models.ts`、WS 事件映射与状态仓库加类型；`Theme`/规则加载只取服务端值，不设另一份玩法常量。
- 新全局提醒画面和城市常驻胶囊按确认稿接入。ResultScreen 与战绩详情增加服务端称号；旧结果缺项则只显示原排名。
- 提醒结束同步现金；资金飘字去重编号，不能只按相同金额判断是否已展示。
- 快速模式使用房间统一速度；全局提醒不吞掉下一玩家投骰时长，普通人物移动 550ms 不变。

## 五、验证与完成条件

实施阶段必须验证：

1. 两种模式均完成第 N 整轮才发一次；N=1、2、5，2/4/8 人与淘汰导致行动顺序绕回。

## 六、实施顺序与系列赛衔接

阶段 A（当前）：规则方案 + 全局提醒/结算称号候选稿 → 用户确认 UI。

阶段 B：收入指标、一次性轮次奖励、趣味称号、对应后台配置/结果存储/客户端 → 回归验证与提交。

阶段 C：城市事件池、确定性触发、安全点预告/生效/结束、经济倍率与后台配置 → UI/多人回归与提交。

阶段 D：B/C完成后增加好友系列赛。复用现有再来一局，但新增独立的 `seriesId`、固定报名名册、计划局数、已完成局号与累计积分；每局只结算积分一次，重连保留，不跨房间泄漏。管理员配置局数、各名次积分和并列算法；房主开赛前选用、局中不能切换。成员退出、补位、机器人与中止局的具体计分规则另出方案和 UI 审阅。本次不提前改房间玩法预设、机器人策略或表情系统。
